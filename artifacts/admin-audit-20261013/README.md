# 개띠랑 관리실 전체 점검·개선 보고서

점검 기준: 2026-10-13, 기준 커밋 `a75bd64`

## 결론

관리실을 “숫자가 많은 화면”이 아니라 대표가 오늘 처리할 일, 매장 판매가능, 전체 장부, 연결 상태, 재정·정산을 서로 다른 근거 수준으로 빠르게 구분하는 실무 도구로 정리했다. 첫 조회 실패를 0건으로 표시하거나, 문서 갱신 중 작성 내용을 덮거나, 견적서를 출력하면서 저장 상태를 바꾸는 것처럼 잘못된 업무 판단으로 이어질 수 있는 문제를 우선 수정했다.

운영 데이터 쓰기, 송금, 메일 발송, 주문·거래 삭제, 권한 확대, 새 인증정보 생성은 하지 않았다. 테스트와 화면 자료는 모두 가상 데이터다.

## 점검 범위

관리실 14개 업무 영역을 실제 동선으로 확인했다.

1. 대시보드
2. 팀 업무
3. 주문
4. 수업 신청
5. 기관 문의
6. 매장 판매가능
7. 전체 상품 원장
8. 통합 운영실
9. 재정 현황
10. 프로그램
11. 고객 이력
12. 출간 알림
13. 업무 찾기
14. 견적·정산·서류

서류실에서는 견적서, 거래명세서, B2B 진행, 거래처, 품목표, 기관 제출 서류, 명단·출석부, 사례비 지급 명세, 작가 정산, 정산 자료실, 링크 모음을 확인했다.

각 화면에서 다음을 공통 점검했다.

- 첫 조회, 재조회, 일부 원본 실패, 오래된 데이터, 빈 상태, 재시도
- 검색, 복합 필터, 정렬, 조건 초기화, 결과 수
- 저장 뒤 재조회, 저장 실패 복구, 반복 클릭, 동시 수정 충돌
- 상세 열기, 취소, Escape, 브라우저 뒤로가기, 초점 복귀
- 1440px 데스크톱과 360px 모바일, 키보드 탐색, 상태 알림
- 로그인 만료 뒤 비공개 DOM과 입력값 제거
- 미확인과 0, 장부와 실물, 문서 확정과 지급 완료, 수집 성공과 거래 확정의 구분

## 메뉴별 구현 내용

### 대시보드·핵심 목록

- 오늘 처리할 주문·발송·문의·신청·입금대기를 중복 없이 우선 표시한다.
- 부분 조회 실패 때 마지막 정상값을 보존하되 현재값처럼 보이지 않게 했다.
- 주문, 신청, 문의, 프로그램, 고객, 출간알림에 검색·필터·정렬·초기화·결과 수를 맞췄다.
- 문의 검색 범위를 기관·담당자뿐 아니라 유형·프로그램·문의 내용까지 넓혔다.
- 저장 실패 시 열었을 때의 과거 상태가 아니라 저장 직전 화면 상태로 되돌린다.
- 직접 주문은 안정적인 요청 ID를 재사용하고 불확실한 응답 뒤 같은 ID로 재조회할 수 있게 했다.
- 출간알림은 행 수가 아니라 고유 이메일 수를 세고, 이메일이 없는 행의 복사 동작을 막는다.

### 팀 업무·업무 찾기

- 검색, 업무 종류, 진행 상태, 정렬, 조건 초기화를 한 줄의 명확한 폼으로 구성했다.
- 지표 카드를 누르면 충돌하는 검색 조건을 지우고 실제 적용 상태를 `aria-pressed`로 표시한다.
- 빈 결과에서 바로 전체 보기로 돌아갈 수 있고 실제 업무 카드로 키보드 초점을 이동한다.
- 업무 디렉터리에 주문·배송, 매장 판매가능, 재정 현황 등 관리실 내장 화면을 연결하고 외부 Notion 원본과 구분했다.

### 매장 판매가능·전체 상품 원장

- 판매가능/품절 확정/확인 필요/예약 있음/입고 예정 필터를 추가했다.
- 카드에서 매장 판매가능, 전체 장부, 예약, 입고예정을 별도 수량으로 보여 준다.
- 실물 근거가 없는 0은 품절 확정으로 만들지 않고 `미확인`을 유지한다.
- 전체 상품 원장에는 분류·소유·장부 상태 복합 필터와 초기화를 추가했다.
- 모바일 표를 카드형으로 바꾸고 각 값의 라벨을 유지했다.
- 오래된 자료는 지난 기록으로 표시하고 36시간이 지나면 수량을 숨긴다.

### 통합 운영실·재정 현황

- 원본 매핑과 SCM 원장이 최신이 아닐 때 PayHere 검토·반영을 차단한다.
- 공식 `결제 내역 조회(상세)` 파일이 기존 가져오기 형식과 호환되지 않음을 화면에서 명시한다.
- 최종 검토 요약에 파일명, 매장, 해시 앞부분, 기간을 남긴다.
- 근거 검토는 항목별 명확한 이름과 확인창을 사용하고 장부가 바뀌지 않았음을 결과에 표시한다.
- 최근 100건 제한을 UI에 표시해 전체 이력처럼 오해하지 않게 했다.
- 재정 거래 조건 초기화를 추가하고 미확인 금액은 0원 대신 `미확인`으로 유지한다.

### 서류실·정산

- 거래명세서 동시 수정 충돌, 견적 기반 인쇄의 상태 변경, 문의 읽기 오류를 수정했다.
- 지급계좌와 정산 자료실에서 조회 오류·빈 상태·이전 확인본을 분리했다.
- 정산 문서 정렬은 표시 문자열보다 기간 종료/시작/생성 시각을 우선한다.
- 탭을 표준 `tablist/tab/tabpanel`로 연결하고 방향키, Home, End, 뒤로가기를 지원한다.
- 문서 확정과 지급 완료는 계속 분리했으며, 계좌번호는 마스킹하고 PDF에 포함하지 않는다.
- 기존 3인 관리자 경계와 비공개 정산 자료 규칙은 변경하지 않았다.

## 아직 운영 반영하지 않은 항목

1. 이 브랜치의 GitHub Pages 배포와 Supabase Edge Function 배포는 하지 않았다. 특히 Edge 함수는 코드 회귀만 통과했으며 운영 수집 재검증 전 별도 배포 승인이 필요하다.
2. 운영 Edge 배포 뒤에만 MoneyPin 4건과 Google Chat 5건을 같은 배치로 다시 넣어 중복 저장, 성공 이력, 마지막 성공 시각, 원장 불변을 확인해야 한다.
3. PayHere 공식 상세 파일은 안정적인 결제 ID가 없고 시간이 분 단위다. 별도 어댑터 결과를 서버의 SKU·중복·가격·재고 검사와 명시 승인 흐름에 연결하기 전까지 자동 반영하면 안 된다.
4. MoneyPin 공식 내보내기는 이메일 전송 방식이다. 현재 확인된 안전 경로는 지정 메일 → IMAP allowlist → 해시·기간·스키마 검사이며, 무인 정기화에는 세션·수신함·민감자료 전송 설계 승인이 더 필요하다.
5. PayHere/SmartStore 수량이 창고 총보유인지 본점 즉시판매가능인지 운영 규칙이 확정되지 않았다. 이 기준과 실물 수량 확인 전에는 과거 차이와 교환품을 자동 보정하지 않는다.
6. `scmsync` 실패 전파 래퍼는 격리 테스트를 통과했지만 운영 경로·LaunchAgent에는 설치하지 않았다. 설치·수동 실행·최근 exit 확인은 별도 운영 변경이다.
7. 인증·RLS·민감정보 경계는 코드, 마이그레이션, 가상 요청과 읽기 경로로 검증했다. 실데이터 쓰기나 권한 확대 시험은 하지 않았다.
